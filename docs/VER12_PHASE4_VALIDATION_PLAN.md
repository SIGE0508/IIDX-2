# Ver.1.2 Phase 4 総合検証計画

計画追加日：2026-11-05。今回は計画のみで、実PLAYERデータの取得・復元・検証は未実施。

開発順序は Phase 3 WARM UP → Phase 3.5 PLAY LIST → Phase 4 総合検証を維持する。
本項目の追加は、保存形式・推薦条件・Phase 3.5の実装範囲を変更しない。

## 1. 検証を二つに分ける

### A. 架空PLAYERによる自動回帰検証

既存の架空PLAYER・決定的なfixture・乱数注入によるテストを維持する。
Phase 3時点の全127テスト、TRAINING出力の42ケースの比較を継続し、
Phase 3.5以降に追加されるテストも含めて総合実行する。

型検査、通常／Pagesビルド、PWA、390px表示、IndexedDB・CSV・JSON
互換性など、既存の総合検証を継続する。実PLAYERの確認でこれらを置き換えない。

### B. 実PLAYERによる推薦品質確認（今回の追加）

公開版から利用者が取得したJSONバックアップのコピーを隔離ローカル環境に
復元し、NEXT TRAININGとWARM UPの適格性・推薦理由・実用上の妥当性を確認する。

これは特定PLAYER・バックアップ取得時点における品質確認である。
自動回帰テストの件数・合否と区別し、全PLAYERへの一般化はしない。

## 2. 入力データと隔離環境

1. 利用者が公開版のDATA画面からJSONバックアップを取得する。
   公開版への操作は通常のバックアップ出力のみとし、公開版へ復元・初期化・
   記録編集を行わない。出力に伴う既存仕様のバックアップ日時更新はあり得る。
2. 元のバックアップは利用者の私有領域に残し、検証にはコピーを使用する。
   コピー先はリポジトリ・worktree・同期共有フォルダの外にある検証専用一時領域とする。
   ファイルを添付・提供する具体的方法はPhase 4開始時に確認する。
3. 開発版をループバックアドレス 127.0.0.1 の専用ポートだけで起動する。
   Pages相当の /IIDX-2/ パスも確認する。公開サイトへ接続して検証しない。
4. 個人用・公開版用の既存ブラウザプロファイルを使わず、永続化しない
   新規ブラウザコンテキストを作る。公開版に接続するタブを同じコンテキストに作らない。
5. URL（scheme/host/port）とコンテキストが検証専用であること、DBが空であることを
   復元前に確認する。ポートの違いだけを唯一の隔離手段にしない。
6. ローカル開発版の既存DATA復元UIを使用する。検証用コンテキストは新規の空環境とする。
   現行アプリでは初回セットアップ中にDATAを開けないため、記録0件の使い捨てPLAYERを
   「後で登録」で作成し、復元で完全に置換する。公開版や他の開発用DBには触れない。
   具体的な実行手順は VER12_PHASE4_REAL_PLAYER_RUNBOOK.md を参照する。

公開版の既存IndexedDB・キャッシュ・localStorageに対する読み書き、削除、
Service Worker解除などを検証手順に含めない。
公開サイト・GitHub・外部解析サービスへ実バックアップを送信しない。

## 3. 復元とデータ利用の確認

- schemaVersion 1を既存の parseBackup / validateBackupReferences / restoreBackup
  経路で処理する。検証を通すために復元バリデーターを緩めない。
- バックアップ取得時点、開発コミット、共通マスター版を検証条件として確認する。
- PLAYERのランプ・SCORE・BP・個人ERETER・PLAYER Radarなどの登録値をそのまま利用する。
  未登録は未登録のままとし、都合のよい仮値を補わない。
- 読み込み互換処理が補う任意項目の既定値と、実記録の変更を区別する。
  復元後のPLAYER、記録件数、ランプ・SCORE・BP・個人ERETER等を元コピーと照合する。
- バックアップに複数PLAYERがある場合、現在のアプリが選ぶPLAYERを確認し、
  利用者が意図するPLAYERかを確認する。切り替えUIは追加しない。
  対象が異なる場合はそこで確認し、バックアップの黙示的な間引きやID変更をしない。
- 不明chartId・不正値などで復元できない場合、検証を停止して原因を報告する。
  マスターとの時点差・参照不整合を調査し、実データの自動修正や削除はしない。
- 推薦の閲覧・入れ替えだけで記録が変更されていないことを確認する。
  実データ検証でQUICK INPUT保存、CSV取込、PLAY LIST編集などは行わない。
  データ変更を伴う回帰確認は架空PLAYERの環境で実施する。

## 4. NEXT TRAININGの確認

既存の純粋関数を読み取り目的で使い、上限前候補とHOME統合プールを調べる。
必要な観測は検証専用の一時スクリプト／メモリ内で行い、アプリへデータや
検証専用ログを埋め込まない。

- mode・phase・mainBandと、その推定に使われた記録の状況。
- 上限前の5カテゴリの候補数と、HOME統合後のユニーク候補数（最大30）。
- EASY／CLEAR／HARD／EXH／挑戦の最終目標別内訳。
  chartIdの重複を二重計上しない。目標選択前の適格目標は別途区別する。
- 表示譜面の曲名・譜面種別・公式／非公式難易度・現ランプ・目標・推薦理由。
- EASY済み譜面のCLEAR/HARD選択について、HC・個人ERETER・主帯との位置関係・
  同帯HCの比較母数と相対順位が、既存判定に一致するか。
- 通常目標の主帯上限、HC/EXH必須条件、挑戦枠の例外と最大1譜面。
- 候補が20〜30に届かない場合、実際の不適格条件・欠損・既達成数から理由を説明する。
  件数を揃える目的で推薦条件を変えない。
- 複数回の入れ替えで直近3回の回避と、不足時の再利用を確認する。
  再現調査では検証側に固定乱数を注入し、通常UIの抽選結果とは区別する。

## 5. WARM UPの確認

- 軽い指慣らし／基礎運指・安定性／精度練習を役割別に確認する。
- 各役割の候補数、表示曲、chartId、公式／非公式難易度、現ランプ、推薦理由。
- 確定段階表、主帯以下、INITIALの保守的な表、CLEAR以上の必須条件。
- 精度練習のHARD以上優先、CLEAR使用時の理由。
- BP0、BP欠損、Notes欠損、SCORE欠損、Radar欠損の扱い。
  SCORE・BP・ランプが同一プレイとは限らないことを前提に評価する。
- 役割間の重複、NEXTとの重複回避、重複が残る場合の候補不足・優先規則。
- 入れ替えの独立性、画面移動・無関係な再描画での保持。
- 適格候補がなければ、その役割を無理に埋めていないこと。
- 利用者本人にも、指慣らしとして重すぎる／軽すぎる、精度練習に余裕があるか、
  理由が納得できるかを確認する。仕様適合と主観的な品質評価を分けて記録する。

## 6. 不適切な推薦が見つかった場合

最初に表示結果と既存仕様を照合し、次を分けて分析する。

1. 実装の不具合（帯・ランプ・欠損・重複・目標選択など）。
2. マスター／バックアップの欠損・時点差・記録の解釈。
3. 仕様どおりだが、このPLAYERには実用上適さない推薦。
4. 利用者への確認が必要な評価。

原因、影響するカテゴリ／役割、入力条件、現在の判定経路、修正案を報告する。
実データ検証を理由に推薦条件や共通マスターを無断で変更しない。
修正を承認された場合は、実値を転記せず独立した架空の境界ケースを設計し、
既存の自動回帰テストで影響を確認する。

## 7. 実データの保存制限と検証後の扱い

- 生バックアップ、復元データ、PLAYER識別情報、実記録の抜粋をソース、
  fixture、docs、Git履歴、公開リポジトリに保存しない。
- 実データから生成した推薦結果・スクリーンショット・ログ・トレースも
  リポジトリへ保存しない。ブラウザ録画／trace等は原則無効にする。
  必要な一時資料は検証専用領域に限り、識別情報を最小化する。
- 全バックアップやPLAYERオブジェクトを標準出力へ出さない。
  保存先・スクリプト引数・ログにPLAYER名／IIDX IDを埋め込まない。
- 検証終了・失敗・中断のいずれでも専用ブラウザコンテキストを閉じ、
  DB・キャッシュを含むコンテキストを破棄する。
- 検証コピー、一時出力、必要に応じて作成した専用プロファイル等は、
  所有する検証専用パスを確認して削除する。他のユーザーデータを削除しない。
  通常の削除であり、復元不能な消去を保証するものではない。
- 利用者の元バックアップはそのまま保持し、自動削除しない。
- 再検証のため保持が必要な場合、対象・保存先・期間を利用者に確認する。
  確認なしに検証コピーを残さない。
- 終了時に実施した破棄と、残存があれば場所・理由を報告する。
- Git状態を前後で比較し、個人データがstageや差分へ混入していないことを確認する。

## 8. 完了報告の書式

### 自動回帰検証（架空PLAYER）

テスト件数・合否、型検査、両ビルド、監査、PWA、ブラウザ回帰を報告する。

### 推薦品質確認（実PLAYER）

このチャットで利用者向けに報告し、実結果を含む文書をリポジトリに追加しない。

- 実施／未実施、開発コミット、マスター版、使用データの取得時点。
- 復元の成功と対象PLAYERの確認（氏名・IIDX IDは掲載しない）。
- NEXT：候補数、目標別内訳、代表的な表示曲・目標・理由。
- WARM：各役割の表示曲・難易度・ランプ・理由。
- 不適切な推薦の有無、原因と未解決点、利用者の品質評価。
- 実施できなかった項目と理由。
- 隔離環境と検証コピーの破棄状況、元バックアップは変更していないこと。

生データ、全記録、不要な個人識別情報は報告に含めない。
利用者の品質評価を取得できていなければ、その項目は未確認と明記する。

## 9. 完了条件

自動回帰と実データ品質確認の結果を別々に説明でき、候補数・目標・役割の
根拠を追跡できること。不適合があれば原因と対応待ちを明示すること。
公開版・既存ユーザーデータに変更を加えず、個人データをGitへ混入させず、
検証環境の後片付けまで確認して完了とする。
